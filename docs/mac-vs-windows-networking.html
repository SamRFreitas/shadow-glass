Shadow Glass — field notes

Two Ways to Open a Socket

Piece 12 got stuck for an entire session on something that had nothing to do with WebRTC, or with our own code being wrong: on macOS, two different APIs that both "open a TCP connection" are not treated the same by the operating system. One of them is gated behind a privacy permission that, in our case, silently never asked. The other — the older, lower-level one — was never gated at all, and had been working perfectly the whole time without us realizing it.

The trail we followed

Every one of these looked, at the time, like it could be the real cause. Documenting the dead ends is as useful as documenting the fix — this exact sequence is what "debugging a silent permission wall" actually looks like in practice.

  1. Maybe it's a stdout buffering bug — we'd hit this exact kind of silence before (piece 5). Ruled out: running in a real terminal (a tty) doesn't buffer this way at all.
  2. Maybe Claude launching it via automation is the problem — no proper GUI session, no Dock icon. Real issue, worth fixing on its own, but the same silence continued even once the user ran it themselves in their own terminal.
  3. Maybe Xcode handles this automatically — try running through Xcode instead of swift run. Xcode's own console showed the real clue by accident: "Cannot index window tabs due to missing main bundle identifier" — this binary had no bundle identity at all.
  4. Embed an Info.plist via a linker flag (-sectcreate __TEXT __info_plist) — gives the raw binary a CFBundleIdentifier without needing a real .app folder. Confirmed embedded (otool -s proved the bytes were there) — but still no Dock icon, still no permission prompt.
  5. Build a real .app bundle (Contents/MacOS/ + Contents/Info.plist), launched via open instead of running the raw binary. Dock icon finally appeared — real progress — but the specific "allow local network access" popup still never showed, and tccutil reset LocalNetwork <bundle-id> found nothing to reset, meaning the OS genuinely never even considered asking.
  6. Check what had worked all along — every single signaling test since piece 10 used nc from a plain terminal, connecting to this exact same Windows machine, on this exact same network, with zero delay and zero popup, every time. That's the real signal: whatever gate was blocking NWConnection never applied to nc at all — because it isn't the network that's gated, it's the specific API used to reach it.

Two APIs, one socket, different rules

NWConnection (Apple's Network framework) and a plain BSD socket() both end up doing the exact same thing at the hardware level — but only one of them passes through a privacy checkpoint first.

Apple's own docs frame the "Local Network" permission (added in macOS Big Sur/iOS 14) as covering Bonjour discovery and connections to devices on private IP ranges (like our 192.168.15.x LAN) made through Network.framework or NSNetService. Plain POSIX sockets predate this permission system by decades and were never folded into it — a genuine gap, not a bug, and one every classic Unix networking tool still relies on today.

The fix: match what Windows already does

signaling_test.cpp was already using raw sockets (Winsock2) — this wasn't a new concept, just a new place to apply it. Winsock was explicitly modeled on BSD sockets in the early 90s, so both sides of Shadow Glass now use, conceptually, the exact same four calls:

Windows (Winsock2)
socket(AF_INET, SOCK_STREAM, ...)
connect(sock, &addr, ...)
send(sock, data, size, 0)
recv(sock, buf, size, 0)
macOS (Darwin/BSD)
socket(AF_INET, SOCK_STREAM, ...)
connect(fd, &addr, ...)
send(fd, data, size, 0)
recv(fd, buf, size, 0)

The only real difference is spelling (SOCKET vs. Int32 for the handle, closesocket() vs. close()) — a direct result of Microsoft copying the Unix networking API rather than inventing a new one. The trade-off for going lower-level than Network.framework: no built-in async completion handlers, so connect() and recv() block, and now run on a background thread instead of blocking the whole app.

Other macOS/Windows particularities found so far

Not every platform difference this project has hit is about networking — collecting the pattern across all of them: the two operating systems each protect and configure things through completely different mechanisms, even when the end goal (run an app, open a connection) looks identical from the outside.

SituationWindowsmacOS
Blocking an inbound connection A network profile (Public/Private) — separate from, and easy to confuse with, the one-time firewall popup that grants an app permission (piece 10's real bug). No equivalent profile concept for a home LAN; instead gates specific APIs per-app (TCC), as this page covers.
Console closing before you can read it Double-clicking an .exe closes its console the instant main() returns — fixed with an explicit getchar() pause inside the program itself. Not applicable the same way — a terminal window stays open regardless of what the program inside it does.
A shared library not found at runtime DLL search order: looks next to the .exe first — fixed with a CMake POST_BUILD copy step. Governed by @rpath — fixed by passing an explicit -rpath at link time.
Giving an app a stable identity Not required at all for a plain .exe to run or open connections. Needs a bundle identifier (Info.plist) before several privacy-gated APIs — including Network.framework — will even prompt, let alone work.

Shadow Glass — field notes

Anatomy of an Offer

SDP (Session Description Protocol) is the plain-text format behind every "Local Description" we've seen. It's not something WebRTC invented — it's a 25+ year old format, originally built for scheduling multicast video conferences, that WebRTC reused because it already existed. That's why some lines below look like unexplained leftovers: they are.

The offer, line by line

This is a real offer our Mac generated during testing. Every line is colored by what it's actually for.

Legacy SDP, barely used by WebRTC Security (DTLS) ICE (finding a path) Data channel config
v=0SDP format version. Always 0 — there has only ever been one.
o=rtc 4159915632 0 IN IP4 127.0.0.1"Origin" line: a fixed username (rtc), a random session ID, a version counter, and a placeholder address. The address here is never actually used to connect — real addresses live in the candidates further down.
s=-"Session name", required by the spec, meaningless for WebRTC — just a dash.
t=0 0Start/stop time — a holdover from SDP's original job of scheduling a conference at a fixed time. WebRTC connections aren't scheduled, so this is always "0 0".
a=group:BUNDLE 0"Bundle everything under identifier 0 onto one connection." We only have one thing (our data channel), so this doesn't do much visible work here — it matters more once audio/video tracks are added later.
a=msid-semantic:WMS *Media-stream bookkeeping, mostly relevant to audio/video tracks — required by the spec, inert for a plain data channel.
a=ice-options:ice2,trickle trickleDeclares "trickle ICE" support — candidates can be sent one at a time as they're found, instead of waiting to gather them all first. This is exactly why we saw two separate "Local Candidate" printouts instead of one block.
a=fingerprint:sha-256 19:1C:1F...The hash of this side's DTLS certificate. Generated by OpenSSL. During the handshake, the other side checks the certificate it receives against this exact fingerprint — proof it's talking to who it thinks it's talking to.
m=application 9 UDP/DTLS/SCTP webrtc-datachannelThe actual offer: "application" data (not audio/video), over the exact UDP → DTLS → SCTP stack from our earlier diagram, formatted as a WebRTC data channel. The port 9 is a placeholder, same story as the address above.
c=IN IP4 0.0.0.0Another placeholder address, same reason as the "origin" line.
a=mid:0This line's own identifier, matching the "0" in the BUNDLE group above.
a=sendrecvThis side will both send and receive (not one-way).
a=sctp-port:5000The SCTP layer's own port number — a logical port inside the encrypted tunnel, unrelated to any actual network/UDP port.
a=max-message-size:262144Largest single message this side accepts on the data channel: 262144 bytes (256 KB).
a=setup:actpassDTLS role negotiation. actpass means "I can play either role, you (the answerer) decide" — only the offering side is allowed to say this.
a=ice-ufrag:/aVbICE username fragment — half of a short-lived password pair.
a=ice-pwd:Lw+1oFBLTzcEgipgNMwLB6The other half. Together, these let each side prove to the other "the candidates I'm about to send you really came from me" during connectivity checks.

Who actually generates each part

Our own code never builds this text by hand — it just calls one function (createDataChannel) and libdatachannel assembles the whole thing, pulling pieces from the different libraries doing the real work underneath.

A candidate line, decoded

Candidates are sent separately from the description (remember the "Local Candidate" printouts). One real example:

a=candidate:2 1 UDP 2114977535 192.168.15.4 62505 typ host

2"Foundation" — groups candidates discovered the same way, for ICE's internal bookkeeping.
1Component ID (always 1 for a plain data channel).
UDPTransport for this candidate.
2114977535Priority — a computed number ICE uses to decide which candidate to try connecting with first.
192.168.15.4The real address — this is the first place an actual, usable IP shows up (the earlier placeholder addresses in the description never mattered).
62505The real UDP port.
typ hostCandidate type: a direct local network address. (Other types exist — "srflx" via STUN, "relay" via TURN — for when a direct path isn't possible; we don't see those on a plain home LAN.)

Offer vs. answer: the one line that actually differs

Line for line, an offer and an answer look almost identical — everything above repeats with fresh random values. Only one attribute changes meaning:

Offer (Mac)
a=setup:actpass
Answer (Windows)
a=setup:active

The offerer proposes either DTLS role is fine; the answerer has to commit to one. This exact detail is how we confirmed, reading a wall of near-identical text during testing, which block was actually which.
